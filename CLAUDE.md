# CLAUDE.md

## Project overview

A 2D, true isometric (2:1) HD pixel-art puzzle game for University of Bristol gamejam with the theme 'Time'. The player records afterimages (clones) of themselves. On every new attempt each earlier clone replays its recorded actions, and the player coordinates the clones to clear rooms: distract or defeat enemies, activate interactables, move objects and collect information.

**Setting and tone:** post-technology, deserted and overgrown, with half-broken relic tech. Puzzle chambers in the spirit of Portal 2. Inspiration only; never copy assets.

**Engine:** Unity (2D), C#, PC target.
- Unity version: 6
- Render pipeline: URP 17.6.0
- Input system: Input System package 1.20.1 (confirm Active Input Handling is set to the new system)

Read `ProjectSettings/ProjectVersion.txt` and `Packages/manifest.json` for accurate values.

**Context:** the jam runs 24 hours (midday Saturday to midday Sunday). Three teammates, each have Claude Code on their own clone of the repo `gamejam-26`.

**Scope source of truth:** the `Ideas/` folder in the repo root (see "Ideas folder" below).
- `Ideas/PROJECT_PLAN.md` holds the overall game idea, the scope lists and the high-level plan for each level.
- `Ideas/<level>.md` (for example `Ideas/tutorial1.md`) holds the detailed design of one level.

Scope lists, as defined in `Ideas/PROJECT_PLAN.md`:
- **Must have:** one complete level with interesting puzzles and working afterimage mechanics.
- **Should have:** enemies and inside/outside variations.
- **Stretch (do not build unless asked):** co-op, lore, easter eggs, NPCs with text speech.

**Priorities, in order:** the game always runs, the core afterimage mechanic, the Must have list, the Should have list, polish. Scope creep is the main project risk, so keep a playable version after every feature.

## Commands

Unity is editor-driven. Claude Code cannot normally run or see the game, so the user confirms in Unity that things compile and behave.

- **Open:** Unity Hub, open the repo root. Do not start Unity from the command line unless asked.
- **Compile check:** Unity recompiles when the editor regains focus. If Unity MCP tools are connected, read the console with them. Otherwise ask the user to report console errors and warnings.
- **Run:** press Play in the editor. The game starts on `Assets/_Project/Scenes/Title.unity` (Build Settings order: Title 0, `Tutorial1.unity` 1, `Tutorial2.unity` 2); `Scripts/Editor/PlayFromTitle` (menu GameJam > Play From Title, on by default, saved per machine) makes Play start from Title whatever scene is open; switch it off to play one chamber directly. Keys: WASD/arrows move, E interact, R save the run into the controlled clone, T retry without saving, F mark the run so dying saves it, 1-5 pick the clone to control from the next restart, hold Tab for the chamber map, Esc pause menu. Edit > Clear All PlayerPrefs resets the Continue save and all rebinds.
- **Build:** Windows standalone from Build Settings, output to `Builds/` (git-ignored). Confirm the settings before the first build and note them here.
- **Tests and lint:** none set up. If Unity Test Framework tests are added, put them under `Assets/_Project/Tests` and note how to run them here.
- **Git** runs in the terminal: `git status`, `git diff`, `git log`, `git pull --rebase`.

## Code conventions

- Standard C# style: PascalCase for types, methods and properties, camelCase for locals and parameters, `_camelCase` for private fields, four-space indents, braces on their own line. Namespace `GameJam.<Feature>`.
- One MonoBehaviour per file, file name equal to the class name. One script per entity or responsibility; split a script once it does two jobs.
- Expose inspector values with `[SerializeField] private`, never public fields. Add `[Header]` or `[Tooltip]` to tunable values so teammates can adjust them without reading code.
- Cache references in `Awake` or `Start`. Do not call `Find`, `FindObjectOfType` or `GetComponent` in `Update`, and avoid allocations in per-frame code. Prefer C# events or `UnityEvent` over direct references between systems.
- Gameplay that must replay identically runs on `FixedUpdate` and the shared tick counter, never on `Time.deltaTime`. Random values that affect gameplay use a seeded generator.
- Comments exist so teammates keep control of the code.
  - Start every script with a short header comment: what it does, what uses it, and where it sits in the game flow.
  - Put `///` summaries on classes and on every public and non-trivial private method, saying what it does and why.
  - Inside long methods, add short step comments that describe the flow ("1. record this tick", "2. apply to clone").
  - Comment the reason for the code, not what the syntax does.
  - Keep comments plain and accurate, and update or delete them when the code changes.
- No dead code, no commented-out blocks and no leftover `Debug.Log`. Keep `Debug.LogWarning` and `Debug.LogError` where they report real problems.
- Prefer the simplest implementation that works. This is a jam, and every teammate must be able to read the code.
- Clean code always with logical flow, modular where possible, and always informative clean comments, without being too long

## Key systems

Status: built and working in Tutorial1 (lasers and death in Tutorial2). Update each item when the code changes.

- **Tick clock** (`Core/TickClock`, execution order -100): counts fixed steps from 0 each attempt. Recording and replay index frames by this tick.
- **Afterimage system** (`Scripts/Afterimage`): `AfterimageRecorder` (on the player, order 50) stores one `ActorFrame` (position, facing, interacted) per tick in a `Recording`. `AfterimageManager` keeps recordings in numbered clone slots and respawns one `AfterimageReplayer` clone per slot each attempt. Clones replay positions and repeat interacts on the same tick, then stand still when their run ends.
- **Clone slots** (rules in `Ideas/gui.md`): `AfterimageManager` holds up to 5 slots; the clone limit is `_maxClones` (per chamber, Tutorial1 = 2), capped by the length of its `_slotColours` list (blue, green, yellow, purple, orange; red means dead). `ControlledSlot` is the slot this run records into: a saved slot (re-recording) or `CloneCount` (new). Its clone does not spawn. `SelectSlot` (keys 1-5 or clicking an icon) sets `PendingSlot`. `EndRun(run, keep)` saves into the controlled slot if `keep`, then switches to the pending slot; with no pending slot, any save (new or re-record) moves on to the next new slot, staying put once all slots are full; a retry keeps the controlled slot. It raises `Changed` (end of run, pick, respawn) and `CloneDied(slot)`; `IsSlotDead` clears on respawn. `Visuals/CloneTint` on the Clone prefab colours the sprite and `AfterimageGlow` from the replayer's `SlotColour`, and turns them red on death.
- **Actors:** `Core/IActor` (`Transform`, `IsClone`, `IsDead`, `Kill()`) is implemented by `PlayerActor` and `AfterimageReplayer`. Interactables (`Interactables/IInteractable`) and triggers talk only to `IActor`. `Actors/Interactor` is shared by player and clone and takes this tick's position, so both reach the same thing.
- **Level reset:** `Core/IResettable.ResetState()`. Resettables register with the static `Core/LevelReset` in `OnEnable` and unregister in `OnDisable`; `LevelReset.ResetAll()` resets the room.
- **Death:** hazards call `IActor.Kill()`. A killed clone (`AfterimageReplayer`) stops replaying, turns red and no longer blocks hazards. A killed player (`PlayerActor.Died`) freezes the room for `GameStateController._deathResetDelay`, then restarts: the run is saved into the controlled clone (like R) if `RunMarked`, otherwise thrown away (like T). `ToggleRunMark` (F or the HUD record button) sets `RunMarked`; it clears on every restart and raises `RunMarkedChanged`. This is how a clone is sent ahead to absorb a laser shot. Both components have a "Kill" context menu for testing. `GameStateController._player` must be wired in every level scene.
- **Lasers** (`Hazards/LaserEmitter`, order 60): charge, fire one shot, show the beam, cool down, on a fixed tick cycle from each attempt's tick 0 (timings in ticks, 50 per second). The shot kills only the first living actor along `_direction` from `_muzzle`, within `_beamRadius` (0.35, covers a 2-cell corridor so nobody can sidestep it); a centre ray finds the wall that ends the beam, and triggers and dead clones never block it. Tutorial2 lasers: charge 80, beam 10, cooldown 30 ticks (first shot at tick 80, then every 120). Hits never change the schedule. `LaserEmitter` draws nothing: it exposes `Phase`/`PhaseProgress` and, per shot, `BeamStart`/`BeamEnd` (raised by `_beamHeight` 0.34 and starting `_beamStartInset` 0.78 along the aim, at the barrel); hits still use the floor line from `_muzzle`. `Visuals/LaserPostVisuals` on the prefab's `Emitter` shows the PixelLab post (idle, charge frames scrubbed across the charge, fire frames across the beam), mirrored with `flipX` for lasers aiming left, and stands it `_standForward` (0.45) along the aim at runtime so it clears the low wall behind (moving along the aim never shifts the firing line); the art only faces away from the camera. `Visuals/LaserBeamVisuals` on `Beam` lays pooled `Lasers/Beam/spr_laser_beam_*` segments (32x24, one half-cell step of the 2:1 diagonal, so they tile pixel-exactly; centre pivot) from start to end with an `spr_laser_impact_*` burst, playing 4 frames across the beam ticks. The post has no collider, so it never narrows a corridor corner. `Interactables/PlayerTrigger` fires a UnityEvent when the live player enters (Tutorial2's exit door uses it to call `Door.Open`).
- **Planned extensions,** only after the Must have list works: a clone par and clones degrading as their count grows (playback jitter).
- **Input:** `Player/PlayerInputReader` (execution order -90) is the only script that reads gameplay input (Input System package, inspector `InputAction` fields with code defaults; keep the scene bindings empty). It exposes `MoveInput`, `ConsumeInteract()`, `MapHeld` (Tab; while held, movement and interact read as nothing, so the player stands still and that idle time is recorded), the `CloneRequested`/`RetryRequested`/`MarkRunRequested`/`SelectCloneRequested(slot)`/`PauseRequested` events, `SetGameplayEnabled(bool)` (off while paused and during the intro; Esc stays on), `SetSkipEnabled(bool)` with `SkipRequested` (any key or left click, only on during a cutscene; checked after pause so an Esc skip never pauses) and `RebindTargets`. Movement is screen-relative; `PlayerMovement._isoVerticalScale` (0.5) makes diagonals follow the iso floor.
- **Key rebinding:** `Player/KeyRebinder` (on GameSystems) is the only other input script. It runs one interactive rebind at a time (keyboard only, Esc cancels, taking a key another target uses swaps the two) and raises `Changed`. Each `Player/RebindTarget` (Move's WASD parts, E, R, T, F, Tab, 1-5; arrows and Esc are fixed) saves to PlayerPrefs `bind.<action>.<bindingIndex>`, reapplied in `PlayerInputReader.Awake`. Binding indices come from the code defaults.
- **Game state and scene flow:** `Core/GameStateController` owns Intro, Playing, Paused, Resetting and LevelComplete. `RequestClone` (R) saves the run, `RequestRetry` (T) discards it; both (and the death restart) run the `ResetRoom` coroutine: take the recording, play the optional rewind, apply a pending switch, reset the room, respawn clones and restart the clock. `RequestSelect(slot)` picks the clone to control next. Keys and HUD buttons call the same methods, and all of them work only while Playing. `Pause()` (only from Playing) sets `Time.timeScale` to 0, which stops FixedUpdate so every tick freezes, and turns gameplay keys off; `Resume()` undoes both. `Start` saves the chamber as the Continue point. `BeginIntro()` (called in Awake by an intro) holds the chamber in Intro with no clock and no gameplay keys, so nothing is recorded; `FinishIntro()` starts the first attempt. `_clonesStartUnlocked` (off in Tutorial1) locks R, T, F and 1-5 until `UnlockClones()`, which raises `ClonesUnlockedNow` once; `Interactables/CloneUnlocker` calls it when the live player first enters its Pit. LevelComplete loads the next Build Settings scene after a delay. Level order follows `Ideas/PROJECT_PLAN.md`.
- **Scenes and saves:** `Core/SceneFlow` (static) is the one place for title and menu scene changes: `NewGame` (clears the save, flags the intro, loads `FirstChamberIndex` 1), `ContinueGame` (never plays the intro), `ConsumeIntro()` (true once after a new game), `QuitGame` (stops Play mode in the editor). Every load resets `Time.timeScale`. `Core/SaveProgress` keeps the build index of the last chamber started in PlayerPrefs `save.chamber`; Continue restarts that chamber fresh, without clones.
- **Rewind (visual only):** `Visuals/RewindEffect` (Rewind prefab, own canvas and `RewindVolume`) plays between attempts while the clock is stopped: cyan scanline overlay and rolling tracking band, the player and every clone (`AfterimageManager.Clones`, each replaying `AfterimageReplayer.Run` backwards) move back along their recordings facing forward (`CharacterSpriteAnimator.FaceAgainstMotion`), `Visuals/GhostTrail` stamps fading afterimages, a flash hides the reset, and on a save a ghost in the new clone's colour marks where the run ended. Length scales with the run (0.55-1.2 s); any key skips it (`PlayerInputReader.SetSkipEnabled`) after a 0.15 s grace. `Visuals/CloneMaterialise` on the Clone prefab beams each clone in at respawn (slot-coloured `spr_fx_spawn_ring_*`, flicker, glow flare). An empty `_rewind` means instant resets.
- **Intro:** `Story/IntroSequence` (the `Intro` object in Tutorial1) plays after New Game or Restart Game, or always with its `_alwaysPlay` testing toggle. The `EntranceDoor` (a mirrored Door sitting in the back-left wall gap; its open visuals are a glowing `Opening` in the door's shape (`placeholder_iso_doorway_light`, unlit, sort order 1 so the wall side face does not hide it) and a volumetric cone light `DoorSpill` shining into the room) opens with its `Visuals/DoorShutter` fully rolled up, the camera looks at it (`IntroCameraFocus`), `UI/DialogueBox` types the guard's line, the player (physics off, moved with `PlayerActor.Teleport`) sprints along `IntroStart` → `IntroInside`, the shutter drops and the door slams (`DoorShutter.SetRaised`, which lifts the panel's sort order while it moves so it shows over the glow; `Door.ResetState`; `CameraFollow.Shake`) and the camera glides back to her (`CameraFollow.Follow(target, snap)`) as she reaches spawn. Skip jumps to the end state. `DialogueBox` (prefab, canvas order 5) is generic: `Show(speaker, line)` types out, `Hide(instant)`.
- **Level wiring:** `PressButton` (latches) → `SignalWire` (red pulse along its LineRenderer, timed in ticks) → `Door.Open`, wired with inspector UnityEvents. `Pit` is a one-way drop that cages only the live player and raises `ActorEntered`/`ActorExited`. `LevelExit` calls `GameStateController.CompleteLevel`.
- **Sprite art hooks:** `PressButton` takes optional unpressed/pressed sprites (set its tint colours to white with real art). `Door` raises `OnOpened`/`OnClosed`; the Door prefab wires them to a `Visuals/SpriteFlipbook` on `Visual` (`PlayForward`/`PlayBackward` of the `Doors/Shutter` frames), and a static `Frame` child draws the doorway. `SpriteFlipbook` with Loop and Play On Enable runs machinery loops (conveyor, console). Characters use `Visuals/CharacterSpriteAnimator` with a shared `CharacterSpriteSet` asset (8 directions, E to SE counter-clockwise, idle plus run frames; a direction without run frames shows idle with a bob), built from a PixelLab export folder via Create > GameJam > Character Sprite Set From Folder, which pivots each frame folder under her lowest foot (idle and run canvases differ). PixelLab may export a direction only as a GIF; split it into `frame_NNN.png` files first.
- **Pit depth (visual only):** `Visuals/PitVisuals` on the Pit draws anyone inside 1.25 units lower via `Visuals/ActorPitDepth` on the character's `Body` child (a `SortingGroup` holding Shadow and Visual). Colliders and recordings keep the floor position. Sorting orders: Floor -100, Hole -98, in-pit button -80, in-pit actors -70, `PitShadow` (unlit) -60, `PitFrontGround` -55, everything else 0. The shadow and front ground fade only while the live player is in the pit, so a clone down there stays hidden.
- **See-through occluders:** `Visuals/OcclusionFader` is the reusable fade for anything that can hide the player (ground, walls, ceilings, tall props). Give it sprites and/or tilemaps plus a faded opacity, and call `SetFaded(bool, instant)`. The pit's front ground uses it at 0.2, including the grass and rubble standing on that slab.
- **Prop collision:** solid props (crates, terminals, rubble) carry a `PolygonCollider2D` diamond on their iso footprint (sprite pivot = footprint centre, width 0.9 of the sprite, height half that); vegetation has no collider and is walk-through.
- **Long wall sprites** (doors, wall panels) sort from the far, higher end of their base, so characters standing anywhere in front draw on top. The door's pivot is its upper-left base corner.
- **Rendering (isometric 2:1):** one `Grid` per level with Isometric cell layout, cell size (1, 0.5). Tilemaps: `Floor` (Chunk mode, order -100), and `Walls`/`Ledges` (Individual mode, colliders merged by a `CompositeCollider2D`) so they Y-sort with characters. The Renderer2D sorts by Custom Axis (0, 1, 0). Sprite pivots go at the feet or footprint centre, with sprite sort point Pivot. The two far walls are full height; the near walls are low ledges.
- **Pixel art:** 64 PPU, 64x32 px floor tiles, characters about 32x64 px, Point filter, no compression, no mipmaps. Every chamber's play camera uses orthographic size 2.8125, which gives an exact 3x pixel scale at 1080p (a deliberately close view; the chamber map shows the rest). `Editor/PixelArtImporter` applies these import settings (pivot bottom-centre; `Floors/` pivot centre) on the first import of any PNG under `Art/`.
- **Chamber map:** `Visuals/ChamberMap` (ChamberMap prefab with a disabled `MapCamera`) is the hold-Tab live overview. At start it copies the floor and wall tilemaps cell by cell into flat `MapFloor`/`MapWalls` tilemaps under the room `Grid` (tile `Art/Placeholders/Tiles/placeholder_map_tile`), then while `MapHeld` its camera (culling mask `Map` only, no post-processing, fitted to `CameraBounds`) draws over the play view; the HUD stays on top. Everything on the map is on the `Map` layer with the unlit sprite material: `MapMarker` children on the Player (white dot), Clone (slot-coloured dot, red when dead, via `CloneTint`), Pit (black diamond), PressButton (yellow dot), Door (red line) and LevelExit (green diamond) prefabs. New gameplay prefabs that matter for planning get a `MapMarker` child too.
- **Lighting:** URP 2D lights. The global light is near black (0.03) and the camera background pure black, so only lit areas read. The player's `Body` carries a soft `VisionLight` (the permanent vignette around the character, inner 0.4, outer 1.9) and a small pale `ImplantGlow`, both neutral white so the player never shares a clone slot colour; clones carry `AfterimageGlow`, tinted per slot by `CloneTint`. Lights never cast 2D shadows (no `ShadowCaster2D`, `shadowsEnabled` off); characters use the `Body/Shadow` blob sprite instead. Point lights are the cues (the ceiling-breach pool over the pit is Tutorial1's "go here" clue). `Visuals/FlickerLight` handles broken lamps, and a global Volume uses `Data/Tutorial1_Volume.asset` (bloom, vignette, colour grade, grain).
- **UI** (layout in `Ideas/gui.md`): uGUI (Canvas plus legacy `Text`, 1920x1080 reference). `UI/HudController` handles the bottom-right F (record), T and R buttons and the level complete panel. The F button turns red with a blinking dot and reads "SAVES ON DEATH" while the run is marked. The R button is framed in the controlled clone's colour, its caption reads "SAVE CLONE N" or "SAVE N → PLAY M", and it pulses after the first hinted button press. `UI/CloneColumn` keeps five pre-placed `UI/CloneIconView` icons on the right edge in step with the slots: saved clones, plus a ghost for the next new one only while it is controlled or picked. `CloneIconView.Show(saved, dead, controlled, pending)` draws a framed row and arrow for the controlled clone, a blinking outline for the picked one, and a shake then red with a skull for a dead one. The R/T/F letters and icon badges show the current keys and follow rebinds. Button frames, the pause/title menu buttons and the dialogue box use the PixelLab `Art/UI/spr_ui_*` sprites (sliced, PPU multiplier 2); icons and glyphs still use `Art/Placeholders/UI/` at 50 PPU, so sliced borders draw at 2x. All UI text uses the Relic Terminal pixel font at multiples of 16 px (16, 32, 48) so it stays crisp; it has A-Z, a-z, digits and basic punctuation only, so check `→` and `·` (R caption) render; Unity draws missing glyphs from a fallback font. The EventSystem uses `InputSystemUIInputModule`.
- **Clone HUD reveal:** `UI/CloneHudReveal` on the HUD root hides the clone parts (CanvasGroups on CloneColumn, CloneButton, RetryButton, RecordButton) while clones are locked and pops them in on `ClonesUnlockedNow`. `HudController` only writes the R button's scale while pulsing, so the two do not fight. At the clone limit the R caption adds "· MAX L" and `CloneIconView.ShowLocked()` puts a padlock (`placeholder_ui_lock`) on the icon just past the limit.
- **Menus:** `UI/TitleMenu` (Title scene) shows Continue only when a save exists, plus New Game and Quit. `UI/PauseMenu` (PauseMenu prefab, canvas order 10 over the HUD, dark backdrop that blocks HUD clicks) routes Esc: it is ignored mid-rebind, goes back from Settings, and otherwise pauses or resumes. Its main page has Resume, Settings, Restart Game (`SceneFlow.NewGame`) and Quit Game. `UI/SettingsPanel` spawns one `UI/KeybindRow` per rebind target, with Reset to defaults and Back. Every menu button is a `MenuButton` prefab instance, so new art replaces them in one place.

## Workflow

- `main` must always open and run. Work on short-lived branches named `<area>/<short-description>`, for example `afterimage/record-replay`. Merge into `main` whenever something works, at least hourly. Run `git pull --rebase origin main` before merging or pushing. Never force-push `main`.
- Each teammate has their own clone and runs one Claude Code session in it. Do not use git worktrees, because each would need its own Unity import.
- Before starting: pull, run `git status`, and check that the files you plan to touch are not another person's current task. If you must change a shared system or someone else's scene, tell the user first.
- Scenes and prefabs are YAML and merge badly. One person edits a given scene at a time, and nobody re-saves a scene they did not mean to change. Never hand-edit `.unity` or `.prefab` files: use the Unity editor or Unity MCP, or give the user editor steps.
- Plan before coding when a task touches more than three files or any shared system: write a short plan and wait for the user's go-ahead. For smaller tasks, proceed.
- Commit after each finished, working task, once the user has confirmed it in Play mode. Push when the user asks. One logical change per commit.
- **Commit format:** `type(scope): imperative summary`, 72 characters or fewer, for example `feat(afterimage): record player position each fixed tick`. Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `assets`. Add a body when the reason or a trade-off is not obvious from the diff.
- **A task is done when:** the code compiles with no new console errors or warnings, you have checked or listed what to test in Play mode, there are no stray debug logs, comments match the code, and this file is current.
- **Report back briefly:** what changed, which files, exact steps to test in Unity, anything you could not verify, any deviation from a file in `Ideas/`, and any update made to this file. If something is unclear, ask one short question instead of guessing.

## Rules and limits

- Build only what the Must have list asks for unless the user says otherwise. Do not start Should have or Stretch features without being told. If a task seems to need extra scope, ask first.
- Do not add packages, plugins, Asset Store items or other dependencies without asking. Do not edit `Packages/manifest.json` or `ProjectSettings/` unless the task requires it and the user agrees.
- Never edit or commit `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` or `Builds/`. Do not change third-party code or assets.
- Do not create or generate art or audio assets unless asked. Use simple placeholder shapes and sprites named `placeholder_*`.
- Use only assets the team made or whose licence allows use in a jam. Record every external asset in `CREDITS.md` when you add it: name, author, source link and licence. Do not use copyrighted assets from other games.
- Do not commit secrets or personal paths.

## Decisions and known issues

- **Decided:** Unity, C#, 2D sprites only with a true isometric 2:1 view (replaced the earlier 3/4 Stardew view), PC target. Scope and level designs live in `Ideas/` (`PROJECT_PLAN.md` plus one file per level).
- **Decided for Tutorial1:** the pit is a one-way drop (the clone key is the only way out), a clone stands still when its run ends, and the "go here" hint is a brighter area, not a trail of dots. The pit's inside is hidden in shadow, the ground turns see-through only for the live player, and vision is a light around the character, not a screen overlay. The only dialogue in the game is the guard's "Come back here!" in the intro.
- **Decided for Tutorial2:** a laser hit on the live player saves the run only if it was marked with F (T always discards), lasers run on a fixed tick timer that hits never reset, each attempt starts at Chamber 2's entrance, and Laser 2 stays dark until the turn. Layout (cells): landing (7..10, 12..15), Corridor 1 west along y 10..11, Corridor 2 south along x -3..-2, exit passage east along y -4..-3 with the door at x 0 opened by `DoorTrigger` (a `PlayerTrigger`).
- **Known issues and workarounds** (add each with a one-line workaround and remove it when fixed):
  - MCP for Unity (a git package) fails with "No 'git' executable was found" if Unity Hub was started before Git was installed (Unity inherits Hub's old PATH). Workaround: quit Unity Hub fully (tray icon too) and reopen it.
  - Painting tilemaps from editor code leaves stale wall colliders. Workaround: after `SetTile`, toggle the `TilemapCollider2D` off and on, call `ProcessTilemapChanges()`, then `CompositeCollider2D.GenerateGeometry()`, and save.
  - After editing a script, a compile can still load the old version (new fields missing). Workaround: request a scripts-only recompile and check the type with reflection before using it.
  - A newly created script can stay out of the compiled assembly (its MonoScript reports no class, no console error). Workaround: delete the new `.cs` and its `.meta`, refresh, write the file again, then refresh.
