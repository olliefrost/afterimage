# CLAUDE.md

## Project overview

A 2D, true isometric (2:1) HD pixel-art puzzle game for University of Bristol gamejam with the theme 'Time'. The player records afterimages (clones) of themselves. On every new attempt each earlier clone replays its recorded actions, and the player coordinates the clones to clear rooms: distract or defeat enemies, activate interactables, move objects and collect information.

**Setting and tone:** post-technology, deserted and overgrown, with half-broken relic tech. Puzzle chambers in the spirit of Portal 2. Inspiration only; never copy assets.

**Engine:** Unity (2D), C#, PC target.
- Unity version: 6
- Render pipeline: URP 17.6.0
- Input system: Input System package 1.20.1 (confirm Active Input Handling is set to the new system)

Read `ProjectSettings/ProjectVersion.txt` and `Packages/manifest.json` for accurate values.

**Context:** the jam runs 24 hours (midday Saturday to midday Sunday). Three teammates, each have Claude Code on their own clone of the repo `gamejam-26`.

**Scope source of truth:** the `Ideas/` folder in the repo root (see "Ideas folder" below).
- `Ideas/PROJECT_PLAN.md` holds the overall game idea, the scope lists and the high-level plan for each level.
- `Ideas/<level>.md` (for example `Ideas/tutorial1.md`) holds the detailed design of one level.

Scope lists, as defined in `Ideas/PROJECT_PLAN.md`:
- **Must have:** one complete level with interesting puzzles and working afterimage mechanics.
- **Should have:** enemies and inside/outside variations.
- **Stretch (do not build unless asked):** co-op, lore, easter eggs, NPCs with text speech.

**Priorities, in order:** the game always runs, the core afterimage mechanic, the Must have list, the Should have list, polish. Scope creep is the main project risk, so keep a playable version after every feature.

## Commands

Unity is editor-driven. Claude Code cannot normally run or see the game, so the user confirms in Unity that things compile and behave.

- **Open:** Unity Hub, open the repo root. Do not start Unity from the command line unless asked.
- **Compile check:** Unity recompiles when the editor regains focus. If Unity MCP tools are connected, read the console with them. Otherwise ask the user to report console errors and warnings.
- **Run:** press Play in the editor. The game starts on `Assets/_Project/Scenes/Title.unity` (Build Settings order: Title 0, `Tutorial1.unity` 1, `Tutorial2.unity` 2, `Chamber3.unity` 3, `Chamber4.unity` 4, `Ending.unity` 5); `Scripts/Editor/PlayFromTitle` (menu GameJam > Play From Title, on by default, saved per machine) makes Play start from Title whatever scene is open; switch it off to play one chamber directly. Keys: WASD/arrows move, E interact, R save the run into the controlled clone, T retry without saving, F mark the run so dying saves it, 1-5 pick the clone to control from the next restart, hold Tab for the chamber map, Esc pause menu. Edit > Clear All PlayerPrefs resets the Continue save, all rebinds and the shake setting.
- **Build:** Windows standalone from Build Settings, output to `Builds/` (git-ignored). Confirm the settings before the first build and note them here.
- **Tests and lint:** none set up. If Unity Test Framework tests are added, put them under `Assets/_Project/Tests` and note how to run them here.
- **Git** runs in the terminal: `git status`, `git diff`, `git log`, `git pull --rebase`.

## Code conventions

- Standard C# style: PascalCase for types, methods and properties, camelCase for locals and parameters, `_camelCase` for private fields, four-space indents, braces on their own line. Namespace `GameJam.<Feature>`.
- One MonoBehaviour per file, file name equal to the class name. One script per entity or responsibility; split a script once it does two jobs.
- Expose inspector values with `[SerializeField] private`, never public fields. Add `[Header]` or `[Tooltip]` to tunable values so teammates can adjust them without reading code.
- Cache references in `Awake` or `Start`. Do not call `Find`, `FindObjectOfType` or `GetComponent` in `Update`, and avoid allocations in per-frame code. Prefer C# events or `UnityEvent` over direct references between systems.
- Gameplay that must replay identically runs on `FixedUpdate` and the shared tick counter, never on `Time.deltaTime`. Random values that affect gameplay use a seeded generator.
- Comments exist so teammates keep control of the code.
  - Start every script with a short header comment: what it does, what uses it, and where it sits in the game flow.
  - Put `///` summaries on classes and on every public and non-trivial private method, saying what it does and why.
  - Inside long methods, add short step comments that describe the flow ("1. record this tick", "2. apply to clone").
  - Comment the reason for the code, not what the syntax does.
  - Keep comments plain and accurate, and update or delete them when the code changes.
- No dead code, no commented-out blocks and no leftover `Debug.Log`. Keep `Debug.LogWarning` and `Debug.LogError` where they report real problems.
- Prefer the simplest implementation that works. This is a jam, and every teammate must be able to read the code.
- Clean code always with logical flow, modular where possible, and always informative clean comments, without being too long

## Key systems

Status: built and working in Tutorial1 (lasers and death in Tutorial2, machines and visual height in Chamber3). Update each item when the code changes.

- **Tick clock** (`Core/TickClock`, execution order -100): counts fixed steps from 0 each attempt. Recording and replay index frames by this tick.
- **Afterimage system** (`Scripts/Afterimage`): `AfterimageRecorder` (on the player, order 50) stores one `ActorFrame` (position, facing, interacted, jumped) per tick in a `Recording`. `AfterimageManager` keeps recordings in numbered clone slots and respawns one `AfterimageReplayer` clone per slot each attempt. Clones replay positions and repeat interacts and jump starts on the same tick, then stand still when their run ends.
- **Clone slots** (rules in `Ideas/gui.md`): `AfterimageManager` holds up to 5 slots; the clone limit is `_maxClones` (per chamber, Tutorial1 = 2), capped by the length of its `_slotColours` list (blue, green, yellow, purple, orange; red means dead). `ControlledSlot` is the slot this run records into: a saved slot (re-recording) or `CloneCount` (new). Its clone does not spawn. `SelectSlot` (keys 1-5 or clicking an icon) sets `PendingSlot`. `EndRun(run, keep)` saves into the controlled slot if `keep`, then switches to the pending slot; with no pending slot, any save (new or re-record) moves on to the next new slot, staying put once all slots are full; a retry keeps the controlled slot. It raises `Changed` (end of run, pick, respawn) and `CloneDied(slot)`; `IsSlotDead` clears on respawn. `Visuals/CloneTint` on the Clone prefab colours the sprite and `AfterimageGlow` from the replayer's `SlotColour`, and turns them red on death.
- **Actors:** `Core/IActor` (`Transform`, `IsClone`, `IsDead`, `Kill()`) is implemented by `PlayerActor` and `AfterimageReplayer`. Interactables (`Interactables/IInteractable`) and triggers talk only to `IActor`. `Actors/Interactor` is shared by player and clone and takes this tick's position, so both reach the same thing.
- **Level reset:** `Core/IResettable.ResetState()`. Resettables register with the static `Core/LevelReset` in `OnEnable` and unregister in `OnDisable`; `LevelReset.ResetAll()` resets the room.
- **Death:** hazards call `IActor.Kill()`. A killed clone (`AfterimageReplayer`) stops replaying, turns red and no longer blocks hazards. A killed player (`PlayerActor.Died`) freezes the room for `GameStateController._deathResetDelay`, then restarts: the run is saved into the controlled clone (like R) if `RunMarked`, otherwise thrown away (like T). `ToggleRunMark` (F or the HUD record button) sets `RunMarked`; it clears on every restart and raises `RunMarkedChanged`. This is how a clone is sent ahead to absorb a laser shot. Both components have a "Kill" context menu for testing. `GameStateController._player` must be wired in every level scene.
- **Lasers** (`Hazards/LaserEmitter`, order 60): charge, fire one shot, show the beam, cool down, on a fixed tick cycle from each attempt's tick 0 (timings in ticks, 50 per second). The shot kills only the first living actor along `_direction` from `_muzzle`, within `_beamRadius` (0.35, covers a 2-cell corridor so nobody can sidestep it); a centre ray finds the wall that ends the beam, and triggers and dead clones never block it. Tutorial2 lasers: charge 80, beam 10, cooldown 30 ticks (first shot at tick 80, then every 120). Hits never change the schedule. `LaserEmitter` draws nothing: it exposes `Phase`/`PhaseProgress` and, per shot, `BeamStart`/`BeamEnd` (raised by `_beamHeight` 0.34 and starting `_beamStartInset` 0.78 along the aim, at the barrel); hits still use the floor line from `_muzzle`. `Visuals/LaserPostVisuals` on the prefab's `Emitter` shows the PixelLab post (idle, charge frames scrubbed across the charge, fire frames across the beam), mirrored with `flipX` for lasers aiming left, and stands it `_standForward` (0.45) along the aim at runtime so it clears the low wall behind (moving along the aim never shifts the firing line); the art only faces away from the camera. `Visuals/LaserBeamVisuals` on `Beam` lays pooled `Lasers/Beam/spr_laser_beam_*` segments (32x24, one half-cell step of the 2:1 diagonal, so they tile pixel-exactly; centre pivot) from start to end with an `spr_laser_impact_*` burst, playing 4 frames across the beam ticks. The post has no collider, so it never narrows a corridor corner. `Interactables/PlayerTrigger` fires a UnityEvent when the live player enters (Tutorial2's exit door uses it to call `Door.Open`).
- **Zones and hold plates:** `Actors/ActorZone` lists the living actors overlapping its collider, refreshed each tick by an overlap query (order -20). It does not use trigger messages, because clones are kinematic triggers and get none against static colliders. `Interactables/HoldPlate` is active only while a living actor stands in its zone and its optional `PowerGenerator` has power; it does not latch.
- **Chamber 3 machines** (`Scripts/Machines`, all tick-timed): `FuelBelt` drops a crate every 60 ticks and carries it to `PowerGenerator.Feed()` in 140 ticks, burning it at `LaserWall` unless blocked. `HydraulicBlock` pushes its block out from a fixed base (arm drawn by `Visuals/PistonArm`) while its pedal `HoldPlate` is held, and springs back otherwise. The generator stays powered for 150 ticks after each crate; `Visuals/PowerLights` fades lights with it. `AllOnGate` (order 70, after replayers) is on while all its `ISignalSource`s are on and fires `_onAllOn`/`_onNoLongerAllOn` as that changes; the exit `DoorLock` uses it with both ledge `PressButton`s and the generator to `Door.Open`/`Door.Close`. `PressButton._requiredPower` (optional signal source) makes a button pressable only while powered. `HoverStairs` (order -10, kinematic) flips its 4 steps up while the raise plate is held and slides to the middle stop if the top-left plate is held, else the left stop if the top-right plate is held, else back right. It carries the live player through `PlayerMovement.AddCarry`, enables its side rails (rows 11..15, so the bottom step is entered from the side) and edge fillers while raised, and stays raised while anyone stands on it. The balcony edge's wall art (`LedgeFace`) never changes: the steps (rows 10..13) climb to the blocks' top, which is the landing, and only the invisible `LedgeEdgeBlockers` open in the stairs' columns. Each step is a parent with a `SortingGroup` at the back of its floor row (so it draws in front of the edge) and an `Art` child that HoverStairs lifts.
- **Chamber 4 machines** (`Scripts/Machines` and `Hazards`, all tick-timed): `TimedDoor` opens a `Door` for `_openTicks` (250) when its wire calls `Trigger()`, then kills anyone in its optional doorway `ActorZone` and closes it; `HoldOpen()` (called by a finished scan) keeps it open for the rest of the attempt. `Visuals/ScannerVisuals` drives the scanning chamber's lamp (dim, open, warning flash, green once scanned) and sweep ring, and fades the booth art to `_occupiedAlpha` while `Scanner.IsOccupied`, so whoever is inside stays visible. `Scanner` fires `_onScanned` once per attempt after a living actor stands in its zone for `_scanTicks` (50). `RisingPlatform` rises over `_moveTicks` from `Raise()` (a `HoldPlate` or `PlatformSequence`), is walkable and counts as ground only when fully up (its `JumpGap` object is then off), and on `Lower()` (or after `_autoLowerTicks`) kills everyone on it who isn't mid-jump; `Visuals/PlatformLiftVisuals` draws the rise, a tiled scissor-lift under it and a drop warning. `PlatformSequence.Begin()` raises its platforms `_staggerTicks` apart. `Hazards/JumpGap` colliders are chasm edges that block walking but not jumps (always toggle the whole object; Unity forgets ignored collisions when a collider turns off). `Hazards/FallZone` (order 65) kills anyone in its chasm who isn't mid-jump or on a raised platform. Falls (FallZone, a platform dropping) kill through `Hazards/Falling.Kill`, whose `Fell` event makes `CharacterSpriteAnimator` drop the sprite and shadow out of sight and fade them (`ActorZone.KillAll` takes an optional kill action for this); a dropping platform keeps sinking while the room is frozen after a death so it is seen to fall away. `Actors/ActorJump` (order -5, on player and clone) holds the jump state: `Begin(dir)`, `IsAirborne`, `StartedThisTick`, `ArcHeight`, and `IsActorAirborne(actor)`. `LaserEmitter._continuous` is a constant lethal beam; `SetPowered(bool)` switches any laser off (a plate's `_onActivated` calls `SetPowered(false)`). `ActorZone.KillAll(spare)` kills its living occupants.
- **Ladders and jumping** (Chamber 4 onward): `Interactables/Ladder` (collider plus `_bottom`/`_top` floor-plan points, `_climbSeconds`) is found by `Actors/LadderClimber` (order -6, on Player and Clone); `PlayerMovement` then moves the player only along the ladder, and `ElevationField` draws anyone on it at `Fraction` × height (side rails in the scene stop people stepping off). `Player/PlayerJump` (order -4) starts `ActorJump` from the jump key in the keys' direction or the last facing (not from a ladder or mid-air); `PlayerMovement` flies the player at `_jumpSpeed` (3) with keys ignored. `ActorJump` and `LadderClimber` sit on both prefabs and need no wiring; `PlayerJump` (wired to the scene's input, clock, movement and climber) and `UI/JumpHint` (a `PlayerTrigger` calls `Show()`; once per visit, hides on the first jump or after 5 s) are added only in scenes with jumping. `CharacterSpriteSet` holds per-direction `Jump` frames and one `Climb` set; `CharacterSpriteAnimator` scrubs jump frames across the jump, adds `ArcHeight`, and loops climb frames (a ping-pong of the PixelLab `ladder-climb` frames, hands on the rungs), falling back to idle plus a bob. On a ladder it draws the character on the wall face via `Ladder.HugOffset` (physics crosses the ladder's cell; the art steps onto the ledge over the last quarter). Ladder art is `Art/Machinery/Ladder/spr_ladder_wall`, drawn for faces rising right, so mirrored on -x faces.
- **Visual height** (physics stays flat): `Visuals/ElevationField` (one per level, optional) gives the ground height at a point: its `_raisedAreas` cell rects, plus the steps via `HoverStairs.StepFraction`. `Visuals/ActorElevation` on the Player and Clone `Body` lifts the Body's children to that height; `CharacterSpriteAnimator` adds `ActorElevation.Height` to its own bob. The Body itself never moves, so sorting stays on the floor plan. Raised art lives on `RaisedFloor`/`RaisedWalls` tilemaps offset +1.0 (one PixelLab wall block is 64 px = 1.0 tall; `ElevationField._height` matches); their physics is on the collider-only `RaisedBlockers` tilemap at floor level.
- **Wiring visuals:** `Core/ISignalSource` (`IsOn`) is implemented by `PowerGenerator`, `HoldPlate`, `PressButton` and `AllOnGate`. `Visuals/SignalCable` lights a floor `LineRenderer` with a travelling pulse while its source is on, and can tint end sprites (stair stop markers). **One wiring style in every level** (Chamber 3's): a 2 px line (width 1/32, square corners), grey when off, a white-cyan charge front, cyan with a looping 0.12 `placeholder_square` pulse while on; routes follow walls (never across open floor where avoidable) with points on 1/16-cell steps; under each line lie the drawn cable pieces from `Art/Machinery/Cables` (made by `AgentScripts/DrawCables.cs`). After adding or moving a floor-level wire, run **GameJam > Lay Cable Art** (`Editor/CableArtLayer`), which rebuilds the scene's `CableArt` root (runs, wall climbs, junction boxes, sorted just under the line); wires sorted above -90 (Chamber 4's raised ones) get their art from their builder instead.
- **Game feel (visual only; no audio yet, every hook below is where its `Ideas/sounds.md` sound goes):** all camera shakes go through static `Visuals/ScreenShake` (`Shake`, or `ShakeAt` a world position, which fades with distance outside the view so off-screen clones barely register); `CameraFollow` applies them (strongest wins, Perlin noise) scaled by `Core/GameSettings.ShakeScale` (Full/Low/Off, PlayerPrefs `settings.shake`, cycled by the Settings page's Screen Shake button). Sizes: tiny 0.02, small 0.04, medium 0.08, big 0.14. Generic bridges wired by inspector UnityEvents: `Visuals/PunchScale.Punch()` (squash-stretch of an art child), `Visuals/ShakeOnEvent.Shake()`, `Visuals/LightFlash.Flash()`, `Visuals/ThumpOnStop` (fires `_onStopped` when a watched transform comes to rest; ignores teleports). All three skip while `LevelReset.IsResetting`, so reset-driven closes and releases stay quiet. ## Workflow

- `main` must always open and run. Work on short-lived branches named `<area>/<short-description>`, for example `afterimage/record-replay`. Merge into `main` whenever something works, at least hourly. Run `git pull --rebase origin main` before merging or pushing. Never force-push `main`.
- Each teammate has their own clone and runs one Claude Code session in it. Do not use git worktrees, because each would need its own Unity import.
- Before starting: pull, run `git status`, and check that the files you plan to touch are not another person's current task. If you must change a shared system or someone else's scene, tell the user first.
- Scenes and prefabs are YAML and merge badly. One person edits a given scene at a time, and nobody re-saves a scene they did not mean to change. Never hand-edit `.unity` or `.prefab` files: use the Unity editor or Unity MCP, or give the user editor steps.
- Plan before coding when a task touches more than three files or any shared system: write a short plan and wait for the user's go-ahead. For smaller tasks, proceed.
- Commit after each finished, working task, once the user has confirmed it in Play mode. Push when the user asks. One logical change per commit.
- **Commit format:** `type(scope): imperative summary`, 72 characters or fewer, for example `feat(afterimage): record player position each fixed tick`. Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `assets`. Add a body when the reason or a trade-off is not obvious from the diff.
- **A task is done when:** the code compiles with no new console errors or warnings, you have checked or listed what to test in Play mode, there are no stray debug logs, comments match the code, this file is current, and you have run the `code-review` skill on the change and fixed or reported its findings. Do the review at the end of every build task, before committing.
- **Report back briefly:** what changed, which files, exact steps to test in Unity, anything you could not verify, any deviation from a file in `Ideas/`, and any update made to this file. If something is unclear, ask one short question instead of guessing.

## Rules and limits

- Build only what the Must have list asks for unless the user says otherwise. Do not start Should have or Stretch features without being told. If a task seems to need extra scope, ask first.
- Do not add packages, plugins, Asset Store items or other dependencies without asking. Do not edit `Packages/manifest.json` or `ProjectSettings/` unless the task requires it and the user agrees.
- Never edit or commit `Library/`, `Temp/`, `Logs/`, `obj/`, `UserSettings/` or `Builds/`. Do not change third-party code or assets.
- Do not create or generate art or audio assets unless asked. Use simple placeholder shapes and sprites named `placeholder_*`.
- Use only assets the team made or whose licence allows use in a jam. Record every external asset in `CREDITS.md` when you add it: name, author, source link and licence. Do not use copyrighted assets from other games.
- Do not commit secrets or personal paths.

- **Known issues and workarounds** (add each with a one-line workaround and remove it when fixed):
  - MCP for Unity (a git package) fails with "No 'git' executable was found" if Unity Hub was started before Git was installed (Unity inherits Hub's old PATH). Workaround: quit Unity Hub fully (tray icon too) and reopen it.
  - Painting tilemaps from editor code leaves stale colliders (removed walls still block). Workaround: after `SetTile`, set the `TilemapCollider2D.compositeOperation` to None, disable it and the `CompositeCollider2D`, re-enable the tilemap collider, call `ProcessTilemapChanges()`, restore the operation, re-enable the composite, `Physics2D.SyncTransforms()`, then `GenerateGeometry()` and save. Tilemaps also keep removed tiles in their palette arrays: copy the cells, `ClearAllTiles()` and paste them back before deleting tile assets.
  - Merging an old branch can bring a scene that uses art main has since deleted (pink/red squares), and saving it in Unity then strips those references. Before opening such a scene, check that every `guid:` it references has a `.meta` on main, and restore missing assets with their original `.meta` first.
  - Unity does not advance Play mode while unfocused, and there is no `unity command` CLI on this machine, so agents cannot play-test through MCP here; the user tests in the editor.
  - Chamber3 fuel crates have no destroy or feed animation yet: a crate burned by the laser or fed to the generator just disappears (`FuelBelt`). Known limitation, to polish later.
  - A SpriteRenderer added from code or the Add Component menu sorts by its Center, not its Pivot, so tall props hide behind walls they stand in front of. Set `spriteSortPoint = SpriteSortPoint.Pivot` on every new renderer (also in scripts that build sprites at runtime).
  - Sprites drawn higher by moving their transform sort as if further back. Lift a child inside a `SortingGroup` (or a Body's children) instead, so the sort point stays on the floor plan.
  - After editing a script, a compile can still load the old version (new fields missing). Workaround: request a scripts-only recompile and check the type with reflection before using it.
  - A newly created script can stay out of the compiled assembly (its MonoScript reports no class, no console error). Workaround: delete the new `.cs` and its `.meta`, refresh, write the file again, then refresh.
